## Context

The failure being designed against is not a caller mistake that better prose would prevent. It
is a three-layer conspiracy:

1. The model reaches for `collection`, because `get_collection` taught it that word.
2. The omp `xd://` bridge deletes unknown keys silently, so the mistake never surfaces.
3. `search_entities` treats "no collection scope" as a valid, successful query.

Layers 1 and 2 are outside this repository. Layer 3 is not, and it is the only one that has to
hold for the contamination to happen. So the fix is stated as a property of the tool rather than
as advice to the caller: **this server cannot be asked an accidentally unscoped search.**

## Goals / Non-Goals

- **Goal:** an omitted collection scope is a loud refusal, not a wide answer.
- **Goal:** one word — `collection` — for the concept, on every tool that takes it, accepting
  every id form the caller might hold.
- **Goal:** the scope actually searched is in the response, so a transcript proves it.
- **Non-Goal:** defending against a harness that drops *known* keys. If omp ever drops
  `collection` itself, the call fails with a missing-required-argument error, which is the
  correct outcome and needs no further mechanism.
- **Non-Goal:** touching `readonly.py`. Collection resolution reads
  `GET /api/2/collections`, already on the allowlist.

## Decisions

### `collection` is required, and `"*"` is the escape hatch

The alternative was an optional `collection` that defaults to all-collections, keeping backward
compatibility. Rejected: that is the present behaviour with a nicer name, and the run above shows
the default is what does the damage. A default cannot be disclosed loudly enough to fix a caller
that never intended to use it.

`"*"` is deliberately ugly and deliberately not a natural-language word. A model that types it
has decided to search everything; a model that omits the parameter gets an error naming both
options. Cross-collection work is real — `similar_entities` and `xref_results` exist for it — so
the capability stays, but it stops being what you get by saying nothing.

Requiring the parameter also means the missing-argument error is generated by FastMCP's own
signature validation, before any code in this repository runs. That is the strongest available
place to put it: it cannot be bypassed by a code path added later.

### `filters={"collection_id": …}` is refused rather than merged

Merging the two would work and would have made the run above succeed at step 1. It is still
wrong: it leaves two spellings live, so the next model learns whichever it happens to see, and
the ambiguity that produced this change survives inside the fix. The refusal is a one-line
message naming the parameter and the value to move, which costs the caller one turn once and
teaches the surface permanently.

The check inspects `filters` for the `collection_id` key specifically. Other `filters` keys are
untouched — `filters` remains the general-purpose exact-match surface it is documented to be.

### Resolution accepts a foreign_id, and caches

The brief the failing run was given carried both forms: collection `874` and foreign_id
`68c4558f5506410ba3e32fce80fe690c`. A tool that accepts only one of them spends a turn on the
conversion, which is the cost this change exists to remove. `get_collection` already resolves
both, so the logic is extracted rather than written: numeric-looking values are validated and
passed through; anything else is looked up by `filter:foreign_id` and its numeric id cached for
the process lifetime.

The cache is keyed on the foreign id and stores the numeric id. It is safe against the only
mutation that matters — a collection's numeric id never changes — and only a *verified*
resolution is stored: the resolver checks that the record it got back carries the foreign id
it asked for, so upstream filter leniency raises instead of caching a plausible wrong id. A
foreign id that resolves to nothing raises the same error `get_collection` already raises,
naming `list_collections`.

Resolution runs *after* the paging validations. The first draft had it first, on the reasoning
that a caller passing both a bad collection and a bad `limit` should hear about the collection
— but resolving a foreign id costs an upstream request, and this spec already promises that an
over-window or negative-paging call sends none at all. Review caught that the promise held only
because every paging test happened to pass a numeric id. The intent survives anyway: the scope's
own refusals — blank, empty list, `"*"` mixed with ids, too many, wrong numeric form — are all
local and run inside the resolver before it issues anything, so a scope that names nothing is
still reported without I/O.

A list is bounded and deduplicated, twice: once on the caller's spellings, so a repeated id
costs one lookup, and once on the resolved ids, so two spellings of one collection do not emit
the same filter twice. One deadline covers the whole resolution phase, mirroring the shrink
loop — without it, N sequential lookups would multiply the per-request budget by N, which is
the amplification that budget exists to prevent.

### The disclosure goes in `searched`, beside the schema scope

`searched` already exists for exactly this purpose and already carries the schema scope, so a
second mechanism would be a second thing to read. It gains one key, `collection`, holding the
resolved numeric ids as a list, or the string `"*"`.

This falsifies the two published scenarios that assert `searched` equals `{"schemata": "Thing"}`
exactly, so the requirement they belong to is MODIFIED with both scenario titles reproduced
verbatim — retitling a scenario is a deletion at archive time.

## Risks / Trade-offs

- **Every existing caller of `search_entities` breaks.** Accepted, and the reason the change is
  worth cutting a release for rather than folding into another. The break is a typed error at the
  first call, not a wrong answer at the hundredth.
- **~20 mocked tests must pass a scope.** Mechanical, but it is also the proof: if the suite still
  passed untouched, the parameter would not be required.
- **One extra request per distinct foreign id.** Bounded by the cache and by the number of
  collections a session touches, which is one in every run observed.
